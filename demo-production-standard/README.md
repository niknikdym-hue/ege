# Производственный стандарт интерактивных демоверсий ЕГЭ

Версия стандарта: 1.0  
Назначение: создание новых интерактивных демоверсий ЕГЭ для Эксамио с минимальным риском предметных, логических, технических и упаковочных ошибок.

Этот стандарт обязателен для каждого нового предмета. Он построен на результатах независимого аудита и исправления демоверсий по русскому языку, физике, математике базового и профильного уровней и обществознанию.

---

## 1. Главный принцип

У демоверсии должен быть **один машиночитаемый источник истины**.

Вручную нельзя независимо редактировать:

- ответы в T123;
- ответы в preview;
- ответы в тестах;
- ответы в отчётах;
- критерии в нескольких файлах;
- отдельный SVG и его встроенную копию;
- список файлов в manifest;
- итоговые максимумы в интерфейсе и документации.

Все производные файлы должны собираться из единой карты экзамена и единой карты заданий. Любой ручной дубль рано или поздно расходится с исходником.

---

## 2. Источник истины

Для каждого предмета в пакет включаются локальные финальные документы ФИПИ:

1. демонстрационный вариант;
2. спецификация;
3. кодификатор.

Они размещаются только в папке `source/`.

Обязательные правила:

- не использовать PDF с пометкой «ПРОЕКТ»;
- не использовать старую редакцию при наличии финальной;
- не ссылаться только на внешний URL;
- каждый PDF включать в manifest с SHA-256;
- в `SOURCE-REGISTER.json` указывать роль файла, точное имя, SHA-256, число страниц и статус `final`;
- для каждого задания хранить страницу условия, страницу ответа и страницы критериев;
- для каждого рисунка хранить страницу официального изображения;
- год источника хранить во внутренних метаданных и показывать в интерфейсе конкретной актуальной демоверсии, но не зашивать в постоянный URL, canonical, Title, Description, Keywords и slug.

Если утверждение не подтверждено финальным комплектом ФИПИ, оно не попадает в пакет. Рабочая пометка:

`НЕ ПОДТВЕРЖДЕНО — ТРЕБУЕТ ПРОВЕРКИ`

## 3. Обязательные стадии

### G0. Инициализация

Создаются:

- постоянный URL страницы;
- префикс всех файлов;
- внутренний номер версии пакета;
- новый ключ `localStorage`;
- список финальных источников;
- пустые карты экзамена, заданий и ассетов.

Статус: `DRAFT`.

### G1. SOURCE GATE

До создания интерфейса подтверждаются:

- количество позиций;
- время экзамена;
- максимальный первичный балл;
- максимумы каждой позиции;
- все варианты «ИЛИ»;
- официальная таблица ответов;
- все схемы частичного оценивания;
- все критерии развёрнутых заданий;
- все зависимости между критериями;
- все общие основания для нуля;
- все официальные изображения.

Статус: `SOURCE_GATE_PASSED`.

Без этого статуса создавать T123 запрещено.

### G2. CONTENT LOCK

Независимо заполняются и сверяются:

- `EXAM-MAP.json`;
- `TASK-MAP.json`;
- `ASSET-MAP.json`;
- `ACCEPTANCE-CASES.json`.

Проверяется арифметика максимумов и количество официальных примеров.

Статус: `CONTENT_LOCKED`.

### G3. Сборка

Из карт автоматически создаются:

- T123-блоки;
- preview;
- встроенные JSON-данные;
- встроенные копии SVG;
- тестовые фикстуры;
- manifest;
- ZIP.

Статус: `BUILD_COMPLETE`.

### G4. Локальная независимая проверка

Запускаются:

- статические проверки;
- unit-тесты scoring engine;
- browser smoke-test;
- тест сохранения попытки;
- тесты мобильных ширин;
- тест целостности ZIP;
- сверка manifest;
- визуальная проверка всех предметных рисунков.

Статус: `LOCAL_TEST_PASS`.

### G5. Release gate

Пакет получает статус `READY_FOR_TILDA_TEST`, только если все обязательные тесты зелёные.

Это **не** означает, что опубликованная страница проверена.

### G6. Публикация в Tilda

После установки всех T123 и публикации проверяются:

- реальный URL;
- старт;
- таймер;
- навигация;
- сохранение и восстановление;
- выбранные варианты «ИЛИ»;
- завершение;
- результаты;
- 320, 360 и 390 px;
- глобальные стили сайта;
- рекламные блоки;
- консоль браузера.

Статус: `PUBLISHED_SMOKE_PASS`.

Только после этого демоверсия считается опубликованной и принятой.

## 4. Обязательная структура пакета

Все служебные файлы лежат на одном уровне с T123. Отдельная папка `00-source-gate/` не создаётся.

```text
<package-root>/
├── 00-README-CODEX.txt
├── <prefix>-PAGE-STATUS.txt
├── <prefix>-SOURCE-GATE.txt
├── <prefix>-SOURCE-REGISTER.json
├── <prefix>-EXAM-MAP.json
├── <prefix>-TASK-MAP.json
├── <prefix>-ASSET-MAP.json
├── <prefix>-ACCEPTANCE-CASES.json
├── <prefix>-IMPLEMENTATION-RULES.txt
├── <prefix>-SEO.txt
├── <prefix>-HEAD.txt
├── <prefix>-T123-01.txt
├── ...
├── <prefix>-PREVIEW.html
├── <prefix>-INDEPENDENT-TEST-EVIDENCE.json
├── <prefix>-TEST-REPORT.txt
├── <prefix>-INSTALLATION.txt
├── <prefix>-MANIFEST.txt
├── source/
│   ├── <final-demo.pdf>
│   ├── <final-specification.pdf>
│   └── <final-codifier.pdf>
├── assets/
│   └── *.svg
├── scripts/
├── tests/
└── <package-name>.zip
```

В ZIP включаются все файлы, необходимые для воспроизводимой проверки. Сам ZIP и manifest не включаются в собственный manifest.

## 5. Карта экзамена

`EXAM-MAP.json` содержит только подтверждённые значения:

- экзамен;
- предмет;
- версия источника;
- число позиций;
- время;
- максимум;
- максимумы частей;
- номера кратких и развёрнутых заданий;
- количество официальных примеров;
- порядок T123;
- постоянный URL;
- storage key;
- статус публикации.

Все значения интерфейса и отчётов берутся из этой карты. Запрещено отдельно набирать `27 заданий`, `210 минут`, `50 баллов` в нескольких файлах.

---

## 6. Карта задания

Для каждого задания и каждого официального примера обязательны:

- `number`;
- `variant`;
- полное условие;
- тип ответа;
- официальный ответ;
- только подтверждённые альтернативные ответы;
- максимальный балл;
- точная схема частичного оценивания;
- страницы PDF;
- источник изображения;
- критерии;
- зависимости;
- позитивные и негативные тесты.

### Альтернативный ответ

Альтернативный ответ допускается только при наличии отдельного подтверждения в финальном PDF.

Для каждого альтернативного ответа указывается:

- точная форма;
- страница источника;
- основание принятия.

Формулировки «возможно также», «логически подходит» или «в старом файле было» не являются основанием.

---

## 7. Типы автоматической проверки

Тип проверки выбирается явно для каждой позиции. Общего универсального нормализатора быть не должно.

### `exact_text`

Точное буквенное значение с явно заданным допустимым преобразованием `ё/е` при необходимости.

По умолчанию отклоняются:

- пробелы;
- знаки препинания;
- дополнительные буквы;
- несколько слов вместо одного;
- латинские символы вместо кириллицы.

### `exact_ordered_digits`

Точная последовательность цифр. Любой лишний символ даёт 0.

Запрещено использовать:

```js
value.replace(/\D/g, "")
```

Такой код превращает неправильный ответ в правильный.

### `exact_unordered_digits`

Порядок цифр не учитывается только при прямом разрешении ФИПИ. Сначала проверяется, что введены только цифры и их точное количество.

### `position_partial`

Частичный балл начисляется по количеству ошибочных позиций при неизменной длине ответа и отсутствии лишних символов.

### `set_difference_partial`

Частичный балл начисляется только при явно заданном числе лишних, отсутствующих или заменённых символов.

### `numeric_exact`

Числовая форма с конкретными правилами:

- разрешена ли десятичная запятая;
- разрешена ли точка;
- разрешён ли знак;
- разрешена ли дробь;
- есть ли допуск;
- нужны ли единицы измерения.

Нельзя автоматически принимать несколько чисел только потому, что они получены другим способом решения.

### `multi_field`

Каждое поле проверяется отдельно. Пример: значение и погрешность.

### `expert_only`

Автоматический официальный балл не вычисляется. Возможна только учебная самооценка с явной маркировкой.

---

## 8. Развёрнутые задания и критерии

Критерии нельзя сокращать до общих фраз вроде:

- «есть существенное продвижение»;
- «выполнена часть решения»;
- «допущена ошибка во включении границы»;
- «модель в целом верна».

Для каждого возможного балла должна быть передана точная смысловая ветвь официальной таблицы.

Обязательно проверяются:

- самостоятельные основания частичного балла;
- альтернативные пути получения одного и того же балла;
- граничные значения;
- обязательные рисунки;
- обязательные формулы;
- ограничения области определения;
- условия, при которых следующий критерий блокируется;
- условия общего нуля.

Самооценка пользователя:

- всегда называется неофициальной;
- не заменяет эксперта;
- не должна автоматически формировать официальный итог;
- может показывать ориентировочную сумму отдельно;
- не может скрывать основания общего нуля.

---

## 9. Неавтоматизируемые условия

Техническая эвристика не может считаться официальным решением.

Примеры:

- счётчик слов;
- определение авторских слов при частичном пересказе;
- проверка опоры на исходный текст;
- оценка полноты комментария;
- оценка доказательства;
- проверка корректности физического рисунка по смыслу.

Для таких условий:

1. технический показатель помечается как ориентировочный;
2. пользователь видит точное правило ФИПИ;
3. вводится явная проверка/подтверждение;
4. официальный итог не имитируется;
5. в тестах проверяются все общие основания нуля.

---

## 10. Зависимые критерии

Каждая зависимость реализуется в двух местах:

1. в интерфейсе — недопустимый выбор блокируется;
2. в функции подсчёта — недопустимое значение независимо исключается.

Недостаточно только визуально отключить поле.

Для каждой зависимости обязательны тесты переходов:

- допустимое → недопустимое;
- недопустимое → допустимое;
- перезагрузка после каждого состояния;
- ручная подмена сохранённого значения;
- итоговая сумма.

Примеры:

- К1 = 0 принудительно обнуляет К2 и К3;
- балл 24.2 не разрешён и не суммируется при 24.1 ниже официального порога.

---

## 11. Предметные изображения

SVG является частью содержания, а не украшением.

Для каждого изображения обязательны:

- источник и страница PDF;
- список предметных инвариантов;
- проверяемые координаты/направления/подписи;
- alt/title;
- отдельный файл в `assets/`;
- автоматическое встраивание в T123 из этого файла;
- проверка идентичности отдельной и встроенной версии.

Запрещено вручную редактировать обе копии.

Минимальные тесты:

- геометрические отношения;
- симметрия;
- направления стрелок;
- обязательные силы;
- подписи;
- положение осей и границ;
- соответствие условию;
- соответствие текстовому решению.

Помимо автоматических проверок выполняется независимая визуальная сверка с PDF.

---

## 12. Состояние попытки

Обязательное состояние:

- статус попытки;
- текущий номер;
- ответы;
- отметки для возврата;
- выбранные варианты «ИЛИ»;
- время начала и окончания;
- завершение;
- учебная самооценка;
- зависимости критериев.

Правила:

- новый пакет получает новый storage key;
- все операции `localStorage` защищаются `try/catch`;
- запрет или переполнение хранилища не должны ломать ввод и навигацию;
- выбранный вариант «ИЛИ» не меняется после перезагрузки;
- таймер хранит абсолютное время окончания, а не только число оставшихся секунд;
- тесты запускаются из текущей папки, без путей `/mnt/data/...`.

---

## 13. Навигация

Фиксированная схема Эксамио:

- зелёный — ответ введён и сохранён;
- оранжевый — отмечено для возврата;
- белый — ответа нет;
- синяя рамка — открытое задание.

Обязательны:

- номер задания;
- состояние;
- таймер;
- «Предыдущее»;
- «Следующее»;
- «Отметить»;
- «Сбросить»;
- «Проверить» или «Завершить» в соответствии с режимом.

На ширинах 320, 360 и 390 px не должно быть горизонтального скролла.

---

## 14. Preview и T123

Preview строится автоматически из:

1. HEAD;
2. T123 в порядке из `EXAM-MAP.json`.

Проверяется:

- каждый T123 присутствует ровно один раз;
- порядок совпадает;
- встроенные JSON разбираются;
- JavaScript проходит синтаксическую проверку;
- нет незакрытых `script` и `style`;
- нет служебных фраз;
- canonical присутствует ровно один раз;
- нет года в постоянных SEO-полях;
- нет горизонтального скролла;
- нет ошибок консоли.

Видимый интерфейс не должен содержать:

- комментарии о локальном пакете;
- инструкции разработчику;
- указания «после установки проверить»;
- SOURCE GATE;
- внутренние статусы;
- тестовые кнопки;
- пути файлов;
- служебные ID, не предназначенные пользователю.

## 15. Обязательные тесты

### 15.1 Позитивные

- каждый официальный основной ответ;
- каждый официальный альтернативный ответ;
- каждый вариант «ИЛИ»;
- каждый максимальный балл;
- каждый допустимый частичный балл;
- десятичная запятая/точка только там, где разрешено;
- допустимые перестановки только там, где порядок не важен.

### 15.2 Негативные

Для каждой краткой позиции:

- лишний пробел в начале;
- лишний пробел в конце;
- внутренний пробел;
- запятая;
- точка;
- буква в цифровом ответе;
- цифра в буквенном ответе;
- лишний символ;
- лишняя цифра;
- пропущенный символ;
- повтор символа;
- правдоподобный, но неофициальный ответ.

### 15.3 Частичный балл

Проверяется каждая ветвь:

- точный максимум;
- один допустимый дефект;
- два допустимых дефекта;
- первый случай, который уже должен давать 0;
- лишняя длина;
- лишний символ.

### 15.4 Развёрнутая часть

- каждый возможный балл;
- каждая альтернативная ветвь критерия;
- каждая зависимость;
- каждый общий ноль;
- максимальная сумма;
- сумма без неофициальной самооценки;
- сохранение после перезагрузки.

### 15.5 Браузер

- старт;
- таймер;
- переходы;
- отметки;
- сохранение;
- перезагрузка;
- завершение;
- карточки разбора;
- все варианты;
- все изображения;
- отсутствие ошибок консоли;
- 320/360/390/768/1280 px.

## 16. Независимая проверка

Автор сборки не утверждает собственный пакет единолично.

Нужны два независимых прохода:

### Контентный проход

Проверяющий не смотрит на старые ответы пакета, а заново сверяет:

- условия;
- ответы;
- критерии;
- максимумы;
- схемы;
- формулы;
- изображения.

### Технический проход

Проверяющий использует только release ZIP и запускает все тесты из распакованной папки.

Нельзя считать независимой проверкой повторный запуск того же генератора без проверки исходных инвариантов.

---

## 17. Manifest и ZIP

Manifest создаётся последним.

Обязательные проверки:

- SHA-256 каждого release-файла;
- три PDF ФИПИ;
- все SVG;
- все T123;
- preview;
- evidence;
- тест-отчёт;
- отсутствие устаревших и проектных файлов;
- отсутствие `__pycache__`, `node_modules`, временных логов и служебных архивов;
- ZIP распаковывается без ошибок;
- после распаковки validator проходит из текущей папки.

ZIP нельзя собирать из рабочего каталога без белого списка release-файлов.

---

## 18. Статусы

Допустимые статусы:

- `DRAFT`;
- `SOURCE_GATE_PASSED`;
- `CONTENT_LOCKED`;
- `BUILD_COMPLETE`;
- `LOCAL_TEST_PASS`;
- `READY_FOR_TILDA_TEST`;
- `PUBLISHED_SMOKE_PASS`;
- `RELEASED`.

Запрещено писать `PUBLISHED_READY`, если реальная страница не проверена.

Если URL возвращает 404, статус не может быть выше `READY_FOR_TILDA_TEST`.

## 19. Правила работы с Codex

Codex получает один полный пакет или распакованный репозиторий, а не набор несвязанных фрагментов.

В `00-README-CODEX.txt` указываются:

- текущая версия;
- финальные источники;
- команда сборки;
- команда тестов;
- команда release-gate;
- состав ZIP;
- что является generated-файлом;
- что запрещено редактировать вручную;
- известные ограничения;
- обязательный production smoke-test.

После задания Codex не должен получать отдельные старые версии как равноправные источники.

Все старые аудиты используются только как журнал, но не как источник текущего состояния.

## 20. Критические запреты

Нельзя:

- добавлять ответы без страницы ФИПИ;
- исправлять официальный ключ «по логике»;
- удалять лишние символы перед проверкой;
- считать технический счётчик официальным;
- сокращать критерии частичных баллов;
- вручную поддерживать несколько копий SVG;
- суммировать самооценку как официальный результат;
- полагаться только на disabled-поле без защиты в расчёте;
- включать PDF «ПРОЕКТ»;
- оставлять внешние источники без локальных копий;
- использовать абсолютные пути тестов;
- копировать старый TEST-REPORT без повторного прогона;
- писать PASS до фактического прохождения теста;
- публиковать служебные комментарии;
- выпускать ZIP без отрицательных тестов;
- менять визуальный стиль одновременно с предметным исправлением без отдельного задания.

## 21. Definition of Done

Новая демоверсия готова к установке в Tilda, когда одновременно выполнено всё:

- финальный комплект ФИПИ локально сохранён;
- SHA-256 источников зафиксирован;
- все задания и варианты имеют source locator;
- все официальные ключи проходят;
- все правдоподобные лишние ключи отклоняются;
- все критерии частичных баллов переданы без смыслового сокращения;
- все зависимости защищены в UI и расчёте;
- неавтоматизируемые основания не имитируются техническими эвристиками;
- отдельные и встроенные SVG идентичны;
- preview собран автоматически;
- browser smoke-test зелёный;
- мобильные ширины зелёные;
- manifest зелёный;
- ZIP зелёный;
- в интерфейсе нет служебного текста;
- статус — `READY_FOR_TILDA_TEST`;
- отчёт честно указывает, что production ещё не проверен.

После публикации требуется отдельный `PUBLISHED_SMOKE_PASS`.
