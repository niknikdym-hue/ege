# 00 — READ FIRST: ОБЯЗАТЕЛЬНЫЙ ВХОДНОЙ РЕГЛАМЕНТ ДЛЯ ИНТЕРАКТИВНЫХ ДЕМОВЕРСИЙ ЕГЭ

**СТАТУС: ОБЯЗАТЕЛЬНО ПРОЧИТАТЬ ДО ЛЮБОЙ РАБОТЫ С ДЕМОВЕРСИЕЙ.**

Этот файл — не новый конкурирующий стандарт и не замена уже существующим регламентам. Он задаёт обязательный порядок чтения, проверки и приёмки, чтобы исполнитель (ChatGPT, Codex или человек) не начинал новый предмет/год «с чистого листа» и не повторял уже найденные ошибки.

Дата фиксации: 10 августа 2026 года.

---

## 1. Иерархия документов: что читать ДО кода

Работа запрещена, пока исполнитель не изучил документы в таком порядке:

### Уровень A — общий стандарт для всех предметов

**Обязательно полностью прочитать:**

`demo-production-standard/README.md`

Это существующий производственный стандарт репозитория. Он прямо зафиксирован как стандарт, построенный на результатах аудита и исправлений демоверсий по русскому языку, физике, математике и обществознанию.

Нельзя начинать новый предмет или год, опираясь только на память о прошлой работе.

### Уровень B — предметный регламент

Перед работой с конкретным предметом обязательно найти и прочитать его актуальные правила/пакетные документы.

Для математики дополнительно обязателен:

`MATEMATIKA-EGE-DEMOVERSII-REGLAMENT-SOZDANIYA-I-PROVERKI.md`

Для любого другого предмета исполнитель обязан найти фактические предметные документы в текущем репозитории/пакете (`IMPLEMENTATION-RULES`, `SOURCE-GATE`, `TASK-MAP`, `ACCEPTANCE-CASES`, предметный README/аудит и т. п.).

**Если предметного регламента нет — нельзя молча выдумывать его из памяти.** Сначала изучаются существующая рабочая демоверсия предмета, её служебные файлы и официальные источники, после чего создаётся/фиксируется предметный профиль.

### Уровень C — документы конкретного года

Обязательно изучаются только актуальные файлы нужного года:

- финальная демоверсия ФИПИ;
- спецификация;
- кодификатор;
- официальные ответы;
- критерии;
- справочные материалы;
- `SOURCE-REGISTER` / `SOURCE-GATE`;
- `EXAM-MAP`;
- `TASK-MAP`;
- `ASSET-MAP`;
- `ACCEPTANCE-CASES`;
- текущие правила реализации пакета.

Нельзя переносить текст, ответы, критерии, изображения, годы, storage key или параметры экзамена из соседнего года без прямой сверки.

### Уровень D — фактическая реализация

Только после A+B+C разрешено открывать/изменять T123, preview, runtime, scorer, assets и ZIP.

## 2. Обязательная фиксация чтения

Перед началом содержательной работы исполнитель должен зафиксировать в рабочем отчёте:

- какие общие документы прочитаны;
- какой предметный регламент прочитан;
- какие PDF и служебные карты конкретного года открыты;
- точный год и предмет;
- база/профиль, если уровней несколько;
- какие старые пакеты считаются только материалом, а не источником истины.

Фраза «я помню правила» не заменяет чтение текущих файлов.

---

## 3. Главный принцип источника

Источник истины по содержанию — **официальный комплект ФИПИ нужного года**, а не:

- старый ZIP;
- предыдущий чат;
- старый TEST-REPORT;
- JavaScript с ответами;
- сторонний образовательный сайт;
- «логически правильный» ответ;
- результат предыдущего аудита без новой проверки.

Существующий пакет можно использовать как техническую основу только после доказательства, что его данные соответствуют текущему источнику.

---

## 4. Нельзя проверять демоверсию только «по смыслу»

Каждый официальный пример задания проверяется как единое целое:

`PDF → текст → типографика → формула → таблица/визуал → действие ученика → фактический контрол → ответ/критерий → scorer → state → browser → результат`.

Если один элемент не проверен, пример не имеет статуса PASS.

Для вариантов «ИЛИ» каждый официальный пример проверяется отдельно.

---

## 5. Literal / typography gate — обязательный для всех предметов

Сверяется не пересказ, а фактическое содержание официального задания:

- каждая буква и цифра;
- знаки препинания;
- кавычки, тире, дефисы, скобки;
- единицы измерения;
- верхние/нижние индексы;
- жирное начертание;
- курсив;
- подчёркивание;
- смысловые выделения;
- подписи и обозначения;
- регистр букв;
- латиница/кириллица;
- номера и буквы вариантов.

Допустимы технически иные переносы строк и семейство веб-шрифта, если они не меняют содержание и начертание.

Нельзя сокращать или «улучшать» официальный текст внутри задания.

---

## 6. Interaction gate — ученик должен реально выполнить действие

Тип элемента ответа определяется **тем, что должен сделать ученик**, а не тем, какой код потом попадает в бумажный бланк.

Примеры:

- короткий числовой/текстовый ответ → input;
- соответствие → отдельный выбор по каждой позиции;
- множественный выбор → checkbox;
- одиночный выбор → radio/select;
- заполнение таблицы → контролы в соответствующих ячейках;
- несколько независимых значений → несколько полей;
- развёрнутое решение → textarea/предметный интерфейс самооценки;
- если разные официальные примеры одной позиции требуют разных действий, контрол зависит от конкретного примера.

Прямая запись в `state`/`localStorage` не является проверкой пользовательского ввода.

Каждый тип ответа проходит реальный browser-test мышью/клавиатурой.

---

## 7. Input hygiene gate

Для каждого типа ответа предметный профиль обязан явно определить:

- допустимые символы;
- недопустимые символы;
- поведение начальных/конечных пробелов;
- внутренние пробелы;
- запятую/точку;
- знак минус/плюс;
- ведущие нули;
- дроби;
- регистр;
- кириллицу/латиницу;
- лишнюю длину;
- повтор символов;
- вставку из буфера;
- пустое и частично заполненное состояние.

**Нельзя использовать универсальный «очищающий» нормализатор, который превращает неправильный ответ в правильный.**

Если предметный интерфейс автоматически канонизирует ввод (например, удаляет крайние пробелы), это должно происходить в самом поле до сохранения и отдельно тестироваться. Внутренние запрещённые символы нельзя молча удалять.

Навигация «ответ дан» должна опираться только на валидное заполнение, а не на непустую строку.

---

## 8. Visual integrity gate — усиленный обязательный контроль

Проверка «картинка похожа» запрещена.

Для **каждого** рисунка, графика, схемы, карты, таблицы как изображения и любого визуального фрагмента выполняется пара `SOURCE ↔ DEMO`.

Проверяется:

- правильный ли это объект;
- полное ли кадрирование;
- не обрезан ли верх/низ/левый/правый край;
- сохранены ли поля, необходимые для чтения;
- все оси;
- названия осей;
- все числовые отметки;
- деления шкалы;
- стрелки осей и направлений;
- точки, линии, штриховки;
- легенда;
- подписи объектов;
- единицы измерения;
- крайние значения шкалы;
- геометрические отношения;
- нет ли чужого соседнего текста, «ИЛИ», линии ответа, водяного знака или части другого задания;
- не потеряны ли данные при WebP/JPEG-компрессии;
- читаемость после фактического CSS-масштабирования;
- desktop и mobile.

### Обязательное правило четырёх краёв

Для каждого визуала отдельно осматриваются **все четыре края**. Если крайняя подпись/деление/стрелка подходит близко к границе crop, нужен дополнительный запас и повторный рендер.

### Графики

Для графика отдельно перечисляются и проверяются:

- ось X;
- ось Y;
- подписи обеих осей;
- все крайние подписи/значения;
- сетка/деления;
- подписи кривых/точек;
- легенда;
- единицы;
- начало и конец видимого диапазона.

Наличие самой кривой при срезанной подписи оси = FAIL.

---

## 9. Formula / scientific notation gate

Для предметов с формулами проверяются два уровня:

1. математическая/научная семантика;
2. буквальное визуальное воспроизведение источника.

Проверяются дроби, степени, индексы, корни, скобки, знаки умножения, функции, прямое/курсивное начертание переменных и операторов, системы, интервалы, единицы и пунктуация вокруг формулы.

«Математически эквивалентно» не является достаточным основанием менять вид официальной формулы внутри задания.

---

## 10. Scorer gate только после Interaction gate

Сначала доказывается, что ученик может правильно ввести/выбрать ответ через реальный UI. Только затем тестируется scorer.

Обязательны:

- официальный правильный ответ;
- неправильный ответ;
- официальные альтернативы;
- правдоподобные, но неофициальные ответы;
- все граничные случаи формата;
- частичные баллы и зависимости, если предусмотрены;
- общий ноль;
- невозможность получить балл через недопустимый формат.

---

## 11. State / reload / navigation gate

Проверяются реальным браузером:

- старт попытки;
- таймер;
- переходы;
- отметка для возврата;
- состояние номера;
- autosave;
- reload;
- восстановление конкретного варианта «ИЛИ»;
- восстановление ответа;
- очистка;
- изменение ответа;
- завершение;
- итог;
- поведение при недоступном `localStorage`;
- отсутствие ложного состояния «ответ дан» при невалидном вводе.

---

## 12. UI/UX и доступность — проверяются как функция, а не украшение

Минимум:

- управление мышью;
- управление клавиатурой;
- видимый focus;
- label/aria для интерактивных контролов;
- disabled-состояния;
- понятные сообщения об ошибке;
- отсутствие перекрытий;
- 320/360/390/768/1280 px;
- отсутствие горизонтального скролла;
- читаемость длинных формул/таблиц/рисунков;
- zoom браузера, если он выявляет обрезание содержимого.

---

## 13. PREVIEW ↔ T123 parity gate

Нельзя проверять красивый PREVIEW и считать, что Tilda получит то же самое.

Обязательно доказать:

- PREVIEW собран именно из текущих HEAD + T123;
- каждый T123 включён ровно один раз и в правильном порядке;
- нет ручной «починки» только в PREVIEW;
- data/runtime одинаковы;
- встроенные assets совпадают с исходными;
- после чистой сборки PREVIEW воспроизводится заново без ручных исправлений.

---

## 14. Tilda size / installation gate

Размер каждого T123 измеряется **до** передачи пользователю.

Предметный порог задаётся предметным регламентом/текущей практикой. Превышение рабочего порога требует разделения блока и полного regression-test затронутой архитектуры.

`READY_FOR_TILDA_TEST` — локальный статус. Он не означает, что опубликованная страница проверена.

`PUBLISHED_SMOKE_PASS` возможен только после установки и проверки живой страницы.

---

## 15. Change control

После любой правки обязателен diff.

- Изменена только пользовательская копия → проверяется copy/UI regression, содержательные данные не переписываются.
- Изменена общая функция ввода → повторно тестируются все контролы, которые её используют.
- Изменён crop/asset → повторно проходит visual integrity gate именно этого визуала и его mobile/desktop.
- Изменена формула/условие → повторно source + literal + formula + browser для затронутых примеров.
- Изменено разбиение T123/runtime → повторно PREVIEW parity + полный browser regression.

Нельзя после точечной правки объявлять полный новый аудит без доказательства; нельзя и сохранять старый PASS для затронутого gate.

---

## 16. GAP REVIEW — обязательный финальный этап

После прохождения всех известных gates проводится отдельный аудит вопроса:

**«Какой класс ошибок мы вообще не проверяли?»**

Это не повтор чек-листа. Проверяющий обязан попытаться придумать/найти новый способ сломать демоверсию.

Минимальные направления gap-review:

- что может быть визуально обрезано, хотя объект «правильный»;
- что может выглядеть верно в PREVIEW, но отличаться в T123;
- что может считаться ответом при невалидном вводе;
- что scorer может «исправить» за ученика;
- что изменится после reload;
- что сломается на другом официальном варианте «ИЛИ»;
- что может быть неверно только из-за начертания/индекса/знака;
- что находится у самого края картинки/таблицы;
- что работает мышью, но не клавиатурой;
- что работает на desktop, но режется на mobile;
- что было уже найдено и исправлено на другом предмете, но не перенесено сюда;
- что содержится в старых аудитах как известный класс дефекта.

Если gap-review нашёл новый класс ошибки, он добавляется в этот master или в предметный регламент **до выпуска следующего пакета**.

## 17. Cross-subject lessons — обязательный перенос уже найденных ошибок

Перед новым предметом/годом исполнитель обязан просмотреть общие уроки предыдущих демоверсий, а не считать их «чужим предметом».

Универсальные уроки уже относятся ко всем предметам, где применимы:

- нельзя заменять требуемое действие ученика универсальным текстовым полем;
- нельзя считать scorer проверкой интерфейса;
- нельзя делать техническую эвристику официальным критерием;
- нельзя молча очищать недопустимый ответ до правильного;
- нельзя сокращать официальные критерии;
- нельзя доверять старому PASS;
- нельзя использовать правильный по смыслу, но визуально повреждённый рисунок;
- нельзя проверять изображение без краёв, подписей и шкал;
- нельзя публиковать служебный текст;
- нельзя считать self-assessment официальным баллом;
- нельзя копировать год/источник/storage из соседнего пакета.

## 18. Evidence-first: что должно остаться после проверки

Для каждого релиза должны быть воспроизводимые доказательства, а не только фраза «проверено»:

- source register;
- exam/task/asset maps;
- acceptance cases;
- audit matrix — одна строка на каждый официальный пример;
- browser log;
- negative-input results;
- visual `SOURCE ↔ DEMO` evidence для каждого содержательного визуала;
- таблица размеров T123;
- manifest;
- clean-extract ZIP validation;
- audit report со всеми найденными и исправленными FAIL;
- список незакрытых пунктов (если есть).

Если доказательства нет — статус считается `UNVERIFIED`, даже если исполнитель уверен, что всё работает.

---

## 19. Независимая проверка

Собственный повторный запуск тех же тестов не является независимым аудитом.

Нужны как минимум два независимых угла проверки:

1. **source/content/visual** — от официального источника к реализации, без доверия старым ответам пакета;
2. **technical/browser/release** — от чистого ZIP к фактическому поведению.

Для критических релизов пакет должен быть пригоден для проверки Codex по приложенным evidence-файлам без необходимости верить текстовому заявлению автора.

---

## 20. Стоп-условия

Нельзя передавать пакет как готовый, если:

- не прочитан `demo-production-standard/README.md`;
- не найден/не изучен предметный профиль;
- не открыты источники конкретного года;
- есть `FAIL`, `UNVERIFIED`, `TODO`, `ASSUMED`;
- не проверен хотя бы один официальный пример;
- нет реального interaction-test;
- нет visual integrity evidence для содержательного визуала;
- не проверены граничные случаи ввода;
- не выполнен gap-review;
- PREVIEW не доказан как сборка текущих T123;
- ZIP не проверен после чистой распаковки.

## 21. Definition of Ready before coding

Кодирование можно начинать только когда:

- прочитан этот `00-READ-FIRST`;
- прочитан `demo-production-standard/README.md`;
- прочитан предметный регламент/профиль;
- открыты источники нужного года;
- составлена карта всех заданий и официальных примеров;
- определено фактическое действие ученика по каждому примеру;
- определены типы ответов и форматные правила;
- перечислены все визуалы и страницы их источника;
- зафиксированы критерии/максимумы/зависимости.

## 23. Предметные дополнения

Этот master задаёт общий обязательный минимум. **Предметный регламент может только усиливать требования, но не отменять общий минимум.**

### Математика

Дополнительно читать:

`MATEMATIKA-EGE-DEMOVERSII-REGLAMENT-SOZDANIYA-I-PROVERKI.md`

Особое внимание: формулы, типографика математических операторов/переменных, соответствия, множественный выбор, графики, геометрические рисунки, полнота осей/шкал/подписей, числовой ввод и его канонизация.

### Русский язык
