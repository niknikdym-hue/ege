# РЕГЛАМЕНТ СОЗДАНИЯ И ПРОВЕРКИ ИНТЕРАКТИВНЫХ ДЕМОВЕРСИЙ ЕГЭ ПО МАТЕМАТИКЕ

> **ОБЛАСТЬ ПРИМЕНЕНИЯ: ТОЛЬКО МАТЕМАТИКА ЕГЭ — БАЗОВЫЙ И ПРОФИЛЬНЫЙ УРОВНИ.**
> Этот файл **не является общим регламентом для русского языка, физики, обществознания или других предметов**. Для других предметов механика ответа, критерии и правила проверки могут отличаться.

Дата фиксации регламента: 9 августа 2026 года.

## 1. Назначение

Этот регламент обязателен при создании, исправлении и финальной проверке интерактивных демоверсий ЕГЭ по математике на Эксамио, в том числе для архивных лет 2025, 2024, 2023 и последующих новых лет.

Главный принцип: демоверсия считается работоспособной только тогда, когда проверено не только содержание и scorer, но и **весь путь ученика от чтения задания до фактического ввода/выбора ответа в браузере**.

## 2. Источник истины

Для каждого года используются официальные материалы ФИПИ соответствующего года:

- демонстрационный вариант;
- спецификация;
- кодификатор;
- официальные справочные материалы и критерии, если они входят в комплект.

Сторонние образовательные сайты не используются как доказательство формата, текста, ответа, критерия или визуала задания.

Перед началом работы необходимо убедиться, что открыты именно файлы нужного года и нужного уровня: база или профиль.

## 3. Что должно быть проверено по каждому официальному примеру задания

Каждый официальный пример/вариант внутри позиции проверяется отдельно.

Для каждого примера фиксируются и сверяются:

1. номер позиции;
2. текст условия;
3. все числа, обозначения и единицы измерения;
4. формулы;
5. выделения текста, если они смысловые;
6. таблицы;
7. рисунки, графики, схемы и иной визуал;
8. подписи к рисункам и таблицам;
9. формулировка действия ученика;
10. фактический тип элемента ответа в демоверсии;
11. правильный ответ;
12. допустимые эквивалентные ответы;
13. критерии и максимальный балл для развёрнутой части;
14. результат сохранения и восстановления ответа;
15. результат проверки ответа в браузере.

Нельзя считать позицию проверенной по одному примеру, если в официальной демоверсии для неё есть несколько примеров через «ИЛИ».

## 4. Правило «ИЛИ»

«ИЛИ» — это структура официального исходника ФИПИ, а не действие ученика.

В интерактивной демоверсии ученик не выбирает «вариант по ИЛИ». Система назначает один официальный пример автоматически при начале попытки и сохраняет этот выбор после перезагрузки.

В пользовательском интерфейсе не должно быть формулировок, создающих впечатление, что ученик вручную выбирает между примерами «ИЛИ».

Допустимая формулировка:

> Для каждой позиции используется один из официальных примеров ФИПИ. Он определяется автоматически при начале попытки и сохраняется после перезагрузки страницы.

## 5. Критически важный interaction-аудит

### 5.1. Проверяется не только ответ, но и способ его ввода

Для каждого задания сначала определяется, **что именно должен сделать ученик**, и только затем выбирается элемент интерфейса.

Нельзя автоматически заменять любое действие универсальным текстовым полем только потому, что в бумажный бланк в итоге записывается последовательность цифр.

### 5.2. Типы элементов ответа

Использовать элемент, соответствующий фактическому действию ученика:

- обычный числовой/краткий ответ → поле краткого ввода;
- соответствие А–Б–В–Г → отдельный выбор под каждой буквой, итоговый код собирается системой;
- «выберите все подходящие варианты» → checkbox/галочки;
- один вариант из нескольких → radio/select;
- заполнение таблицы → отдельные поля или select непосредственно в структуре таблицы;
- развёрнутое решение → textarea/поле решения с отдельной процедурой самостоятельной оценки по критериям.

Если внутри одного номера разные официальные примеры требуют разных способов взаимодействия, **тип контрола должен зависеть от конкретного выпавшего примера**, а не только от номера задания.

### 5.3. Для каждого интерактивного контрола обязательно проверить в браузере

- можно ли физически выполнить требуемое действие;
- неполный ответ;
- полный ответ;
- изменение ответа;
- очистку ответа;
- повторный выбор;
- сборку итогового значения для scorer;
- правильный ответ;
- неправильный ответ;
- допустимую альтернативу, если она предусмотрена;
- autosave;
- восстановление после reload;
- корректное состояние номера задания в навигации.

Программная подстановка значения напрямую в state/localStorage **не считается проверкой пользовательского ввода**.

## 6. Scorer

Scorer проверяется только после проверки interaction layer.

Для кратких ответов проверяются:

- правильный ответ;
- неправильный ответ;
- десятичная запятая/точка там, где это допустимо;
- отрицательные значения;
- ведущие/лишние пробелы, если нормализуются;
- все официально допустимые перестановки или альтернативы;
- заведомо некорректные/лишние символы.

Для заданий на соответствие scorer получает ответ, автоматически собранный из отдельных пользовательских контролов.

Для множественного выбора scorer получает множество выбранных вариантов, а не строку, которую ученик вынужден вручную кодировать.

## 7. Развёрнутая часть профильной математики

Задания с развёрнутым ответом не должны имитировать автоматическую официальную проверку, если её нельзя воспроизвести надёжно.

Обязательно:

- поле для решения;
- официальные критерии соответствующего года;
- официальный максимум баллов;
- самостоятельная оценка ученика отделена от автоматически проверяемой части;
- самостоятельная оценка не должна незаметно изменять официальный автоматический результат краткой части;
- интерфейс должен явно различать автоматический результат и самостоятельную оценку.

## 8. Визуал и формулы

Если рисунок, график, схема, таблица или формула относятся к условию задания, они являются частью задания и проверяются наравне с текстом.

Нельзя ставить PASS, если:

- рисунок заменён приблизительной реконструкцией и не сверён с оригиналом;
- потеряны подписи/масштаб/ось/штриховка/геометрические отношения;
- формула визуально или семантически отличается от источника;
- исчезло смысловое выделение;
- таблица изменила структуру;
- визуал обрезан или плохо читается на рабочей ширине.

## 9. Справочные материалы и линейка

Не создавать впечатление, что линейка является виртуальной кнопкой, если такого инструмента в демоверсии нет.

Рекомендуемая пользовательская формулировка:

> Во время выполнения работы можно пользоваться линейкой. Справочные материалы ФИПИ доступны по кнопке «Справочные материалы».

Справочные материалы в демоверсии должны соответствовать официальному комплекту выбранного года.

## 10. Блок источника в интерфейсе

Не перегружать страницу юридическими и служебными оговорками.

Рекомендуемый формат для базы:

> **Источник:** официальная демоверсия ЕГЭ по математике базового уровня ФИПИ.  
> Интерактивная версия подготовлена Эксамио.  
> Открыть материалы ФИПИ ↗

Для профиля заменить уровень на профильный.

Не добавлять без необходимости длинные пояснения о том, что Эксамио не является ФИПИ/Рособрнадзором, и не перечислять в пользовательском тексте все служебные документы, если это не помогает ученику.

## 11. Таймер, навигация и сохранение

Обязательно проверить реальным браузерным прохождением:

- запуск попытки;
- таймер;
- переход «Следующее/Предыдущее»;
- переход по номерам;
- состояние «ответ сохранён»;
- отметку для возврата;
- очистку ответа;
- autosave;
- reload;
- восстановление выбранного официального примера;
- восстановление ответа;
- завершение попытки;
- невозможность случайно потерять введённые ответы;
- корректное отображение результата после завершения.

## 12. Проверка размеров T123 для Tilda

Размер каждого блока T123 проверяется до передачи пользователю.

Для математических демоверсий используется консервативный внутренний порог: **желательно менее 45 000 байт на один T123**.

Это внутренний технический порог проекта, а не заявленный официальный числовой лимит Tilda.

Если блок превышает рабочий порог, его необходимо разделить заранее, не меняя механику экзамена.

После разделения обязательно провести регрессионный browser-test.

## 13. Правило минимальной правки

Если пользователь просит точечное изменение, не надо заново переписывать содержательную часть, которая не относится к правке.

После точечной правки:

1. сравнить файлы до/после;
2. убедиться, что изменены только целевые части;
3. проверить регрессию изменённой функции;
4. не объявлять необходимость нового полного содержательного аудита, если тексты, формулы, картинки и данные заданий побайтно не менялись.

Если содержательная часть действительно менялась, соответствующие задания повторно проходят source-аудит.

## 14. Статусы

Запрещено использовать общий `PASS`, если проверена только часть системы.

Допустимы отдельные статусы, например:

- `SOURCE_GATE_PASS` — проверены источники;
- `CONTENT_FIDELITY_PASS` — сверено содержание;
- `INTERACTION_GATE_PASS` — реальные способы ввода/выбора ответов пройдены в браузере;
- `SCORER_GATE_PASS` — проверена логика оценивания;
- `TILDA_SIZE_GATE_PASS` — блоки укладываются во внутренний технический порог;
- `READY_FOR_TILDA_TEST` — локальная сборка прошла необходимые локальные проверки;
- `PUBLISHED_SMOKE_PASS` — только после фактической публикации на Tilda и живого smoke-test.

Нельзя писать `FINAL_AUDITED`, `FINAL PASS` или аналогичную формулировку, если отсутствует доказуемая проверка всех необходимых gates.

## 15. Финальный контроль перед ZIP

Перед передачей пакета пользователю проверить:

- правильный год во всех именах файлов пакета;
- база/профиль не перепутаны;
- актуальные PDF-источники;
- все официальные примеры;
- взаимодействие ученика в каждом типе ответа;
- scorer;
- критерии развёрнутой части;
- таймер;
- навигацию;
- autosave/reload;
- справочные материалы;
- T123 размеры;
- PREVIEW;
- отсутствие временных/служебных файлов;
- манифест;
- чистую распаковку ZIP.

## 16. Нейминг по годам

Год обязателен в именах рабочих архивов, пакетов и версий, поскольку материалы разных лет хранятся одновременно.

Примеры:

- `ege-matematika-baza-demoversiya-2025-vX.Y.zip`;
- `ege-matematika-profil-demoversiya-2025-vX.Y.zip`.

При этом год не зашивается в постоянный URL страницы, canonical, Title, Description и slug долгоживущей страницы Эксамио.

## 17. Рабочий порядок для следующего года

Для каждого следующего года порядок такой:

1. открыть официальные PDF нужного года;
2. составить карту всех позиций и всех примеров «ИЛИ»;
3. определить для каждого примера требуемое действие ученика;
4. спроектировать соответствующий тип input/select/checkbox/radio/textarea;
5. перенести текст, формулы и визуал;
6. проверить правильные ответы и критерии;
7. пройти каждый тип взаимодействия руками/автоматизированным браузерным кликом через реальные DOM-контролы;
8. проверить scorer;
9. проверить autosave/reload/navigation/timer;
10. проверить размеры T123;
11. выполнить регрессию;
12. собрать чистый ZIP;
13. присвоить только те gate-статусы, которые реально подтверждены.

## 18. Главный запрет

**Нельзя считать интерактивную демоверсию проверенной только потому, что правильные ответы находятся в JavaScript и scorer возвращает ожидаемые баллы.**

Проверка завершена только тогда, когда подтверждено, что ученик может корректно выполнить каждое задание через фактический интерфейс демоверсии и получить корректный результат.
