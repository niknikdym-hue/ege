Нельзя придумывать новый формат там, где формат уже утверждён. Нельзя переносить экзаменационные данные между годами. Нельзя «заодно» менять принятые версии других лет.

3. SOURCE GATE ДЛЯ КАЖДОГО ГОДА

До сборки обязательно открыть демоверсию, спецификацию и кодификатор ФИПИ именно нужного года и самостоятельно установить:
- число заданий;
- время экзамена;
- максимальный балл и модель оценивания;
- все официальные примеры по каждой позиции;
- точные официальные ответы;
- тип ответа/контрола каждого примера;
- необходимые рисунки, графики, таблицы, формулы и справочные материалы.

Запрещено брать из другого года задания, ответы, время, число заданий, баллы, критерии и особенности ввода. Технический референс другого года не является источником содержания.

4. ОФИЦИАЛЬНЫЕ ПРИМЕРЫ

Если у позиции несколько официальных примеров, в попытке назначается один официальный пример по принятой механике. Назначенный пример:
- хранится в state;
- не меняется после reload;
- виден ученику;
- используется при проверке ответа и в итогах.

Обязательная подпись в интерфейсе: «ФИПИ YEAR · официальный пример V» либо полностью эквивалентный уже утверждённый вариант.

НОМЕР ОФИЦИАЛЬНОГО ПРИМЕРА НЕ СКРЫВАТЬ. Это уже было ошибкой в профильной математике 2025.

5. УСЛОВИЯ И ИЗОБРАЖЕНИЯ

Ориентироваться на принятую подачу базы 2026. Не менять визуальную систему без отдельного задания пользователя.

Если официальный фрагмент используется изображением:
- сохранить условие, формулы, рисунки и подписи без смысловых изменений;
- не перерисовывать предметные элементы;
- не обрезать значимые части;
- проверить читаемость desktop/mobile.

Если внутри официальной картинки внизу есть печатное «Ответ: ____», а ниже в Эксамио уже есть собственное поле ответа, из изображения убрать ТОЛЬКО печатное «Ответ» и линию. Системное поле «Ответ» Эксамио НЕ трогать. Условие, формулы, рисунки и остальное изображение НЕ менять.

Если условие воспроизводится текстом/HTML, нужна посимвольная сверка с ФИПИ и отдельная проверка формул/спецсимволов.

6. КОНТРОЛЫ И INPUT CONTRACTS

Тип контрола определяется официальным заданием, а не удобством реализации.

Для каждого официального примера со свободным вводом должен быть явный индивидуальный input contract. Валидация формата и правильность ответа — разные вещи. Нельзя выводить допустимый формат из правильного ответа.

Raw invalid input не удалять молча: ученик должен видеть сохранённое введённое значение.

Точку нормализовать в запятую только там, где десятичный ввод разрешён конкретным contract.

Matching/selects/checkboxes/row-selection реализовывать реальными DOM-controls. Автотест должен работать теми же контролами, что ученик.

7. SCORER GATE

Для КАЖДОГО официального краткого примера проверить минимум:
- правильный ответ -> правильный балл;
- заведомо неправильный ответ -> 0.

Отдельно проверять пограничные форматы конкретного задания: пусто, пробелы, минус, запятая/точка, проценты, единицы, дроби, лишние символы, неполное число и другие ограничения input contract.

Если хотя бы один неправильный ответ засчитывается как правильный — NO GO.

Баллы и наличие/отсутствие перевода результата брать только из спецификации данного года.

8. STATE / AUTOSAVE / NAVIGATION

Обязательно сохраняются и восстанавливаются:
- назначенные официальные примеры;
- ответы;
- отметка «вернуться»;
- текущая позиция, если это часть движка;
- состояние попытки;
- таймер/дедлайн, если он предусмотрен экзаменом и движком.

Reload не должен менять назначенные варианты или стирать ответы.

Навигация остаётся в утверждённой системе Эксамио: номера заданий, заполнено/не заполнено, отметка для возврата, текущая позиция, назад/далее, завершение, таймер при его наличии.

9. РЕЗУЛЬТАТ ПОПЫТКИ

Для краткой части показывать:
- № задания;
- «ваш ответ»;
- официальный ответ именно назначенного примера;
- начисленный балл.

Склейка текста, возникающая только при копировании результата из браузера в чат, сама по себе не считается UI-дефектом — сначала проверять реальный экран.

Для профильной математики/физики/химии с развёрнутыми ответами действует отдельный обязательный стандарт:
  eksamio-learning-engine/130-EXTENDED-ANSWER-INPUT-UX-STANDARD.txt

Он требует показывать собственный ответ ученика рядом с официальным решением/критериями и, где нужно, давать предметную панель специальных символов. Для базы не добавлять развёрнутую механику, если её нет в официальной структуре года.

10. TILDA / T123 / ПАКЕТ

- Платформа: Tilda, основной код T123, шапка/футер отдельно.
- Каждый T123 строго < 45000 байт; безопасная рабочая цель около 42500 байт.
- Имена папок, файлов, ZIP и внутренних версий должны содержать год.
- INSTALLATION обязан содержать точный порядок T123.
- Финальный пакет не должен содержать __pycache__, .pyc и иной мусор.
- Если правится уже опубликованная принятая версия — менять минимально возможное число T123 и точно перечислить пользователю, что перезаливать.

11. SEO / URL / ГОД

Для evergreen-страниц не зашивать год в постоянный URL/canonical/SEO без отдельного решения. Для архивных годовых страниц использовать уже принятую архивную схему, а не придумывать новую. В интерфейсе конкретной годовой демоверсии год видим обязательно.

12. АВТОМАТИЧЕСКАЯ ПРИЁМКА ДО TILDA

До передачи финального ZIP обязательно:
- пройти каждый официальный пример через реальные DOM-controls;
- для каждого короткого примера проверить correct + wrong;
- проверить все individual input contracts;
- проверить scorer;
- проверить state restore;
- проверить full-correct attempt;
- проверить итоговый экран;
- проверить JS errors;
- проверить widths 1280, 768, 390, 360, 320;
- проверить horizontal overflow;
- проверить T123 size gate;
- повторить критические тесты на ЧИСТОМ распакованном финальном ZIP.

13. НЕЗАВИСИМЫЙ СОДЕРЖАТЕЛЬНЫЙ ВТОРОЙ ПРОХОД

Перед финалом заново, независимо от первичной сборки:
- сверить все ответы с ФИПИ;
- сверить task/example map;
- сверить condition assets с нужными примерами;
- сверить scorer с фактически назначенными примерами;
- сверить input contracts и пограничные случаи.

Внутренний второй проход не называть сторонней/third-party сертификацией.

14. РУЧНАЯ УЧЕНИЧЕСКАЯ ПРИЁМКА И LIVE GO

После публикации:
1) production smoke;
2) пользователь проходит демоверсию как ученик;
3) сверяются назначенные примеры и ответы;
4) проверяются правильные и намеренно неправильные ответы;
5) reload/state/mark/navigation;
6) финальный результат.

LIVE GO запрещён до фактического завершения ручной приёмки.
