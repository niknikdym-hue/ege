ЕДИНЫЙ СТАНДАРТ СОЗДАНИЯ ИНТЕРАКТИВНЫХ ДЕМОВЕРСИЙ ЕГЭ ДЛЯ ЭКСАМИО

Версия: 1.0

Цель: минимизировать, а для уже выявленных системных дефектов — исключить повторение ошибок при создании новых демоверсий.

============================================================
1. ГЛАВНЫЙ ВЫВОД
============================================================

Основная причина ошибок в уже собранных демоверсиях — ручное дублирование одних и тех же данных в T123, preview, тестах, отчётах, критериях, SVG и manifest.

Новая базовая архитектура:

Финальные PDF ФИПИ
        ↓
SOURCE REGISTER + EXAM MAP + TASK MAP + ASSET MAP
        ↓
независимая содержательная проверка
        ↓
CONTENT LOCK
        ↓
автоматическая генерация T123 / preview / tests / manifest / ZIP
        ↓
локальный release-gate
        ↓
установка в Tilda
        ↓
production smoke-test

У каждой демоверсии должен быть один машиночитаемый источник истины. Ответы, критерии, максимумы, изображения и отчёты нельзя независимо редактировать в нескольких местах.

============================================================
2. ИСТОЧНИКИ
============================================================

Для каждого предмета в пакет обязательно включаются локальные финальные документы ФИПИ:

1. демонстрационный вариант;
2. спецификация;
3. кодификатор.

Файлы размещаются только в папке source/.

Обязательно:

- не использовать PDF с пометкой «ПРОЕКТ»;
- не использовать старую редакцию при наличии финальной;
- не ссылаться только на внешний URL;
- фиксировать SHA-256 каждого PDF;
- указывать для каждого задания страницу условия и ответа;
- для развёрнутых заданий указывать страницы критериев;
- для каждого рисунка указывать страницу официального изображения;
- не зашивать год в постоянный URL, canonical, Title, Description, Keywords и slug.

Если утверждение не подтверждено финальными документами:

НЕ ПОДТВЕРЖДЕНО — ТРЕБУЕТ ПРОВЕРКИ

Такое утверждение не включается в рабочую демоверсию.

============================================================
3. ОБЯЗАТЕЛЬНЫЕ СТАДИИ
============================================================

G0 — DRAFT

Создаются URL, префикс файлов, версия пакета, новый storage key и пустые карты.

G1 — SOURCE_GATE_PASSED

До создания T123 подтверждаются:

- количество позиций;
- время экзамена;
- общий максимум;
- максимум каждого задания;
- все варианты «ИЛИ»;
- все официальные ответы;
- все схемы частичного оценивания;
- все критерии;
- все зависимости;
- все общие основания нуля;
- все официальные изображения.

G2 — CONTENT_LOCKED

Независимо проверяются:

- EXAM-MAP.json;
- TASK-MAP.json;
- ASSET-MAP.json;
- ACCEPTANCE-CASES.json.

До CONTENT LOCK создавать финальные T123 нельзя.

G3 — BUILD_COMPLETE

Из карт автоматически создаются T123, preview, встроенные JSON, встроенные SVG, test fixtures, manifest и ZIP.

G4 — LOCAL_TEST_PASS

Запускаются unit-тесты, browser smoke-test, проверка сохранения, мобильных ширин, manifest, ZIP и изображений.

G5 — READY_FOR_TILDA_TEST

Пакет локально проверен и готов к установке. Это ещё не production PASS.

G6 — PUBLISHED_SMOKE_PASS

После публикации проверены реальный URL, старт, таймер, навигация, сохранение, результат, мобильные ширины и консоль браузера.

============================================================
4. ОБЯЗАТЕЛЬНЫЕ КАРТЫ
============================================================

EXAM MAP содержит:

- число заданий;
- число официальных примеров;
- время;
- максимум;
- максимумы частей;
- список кратких и развёрнутых заданий;
- позиции с «ИЛИ»;
- позиции с частичным баллом;
- зависимости;
- общие основания нуля;
- позиции с ассетами;
- порядок T123;
- URL;
- storage key.

TASK MAP для каждого задания содержит:

- номер и вариант;
- полное условие;
- тип ответа;
- официальный ответ;
- подтверждённые альтернативные ответы;
- максимум;
- схему частичного балла;
- страницы PDF;
- критерии;
- зависимости;
- основания нуля;
- связанные изображения;
- обязательные тесты.

ASSET MAP содержит:

- канонический SVG или другой ассет;
- страницу PDF;
- координаты и предметные инварианты;
- обязательные подписи;
- направления стрелок;
- правила встраивания;
- проверку идентичности отдельной и встроенной версии.

ACCEPTANCE CASES содержит:

- все позитивные примеры;
- все альтернативные ответы;
- все ветви частичного балла;
- все негативные формы ввода;
- зависимости;
- общие основания нуля;
- ожидаемый балл для каждого случая.

============================================================
5. ПРАВИЛА ПРОВЕРКИ ОТВЕТОВ
============================================================

Общий универсальный нормализатор запрещён.

По умолчанию любой лишний символ даёт 0.

Нельзя использовать очистку вида:

value.replace(/\D/g, "")

Она превращает неправильный ответ в правильный.

Для каждой позиции выбирается явный тип проверки:

- exact_text;
- exact_ordered_digits;
- exact_unordered_digits;
- position_partial;
- set_difference_partial;
- numeric_exact;
- multi_field;
- expert_only.

Порядок цифр игнорируется только там, где это прямо разрешено ФИПИ.

Альтернативный ответ принимается только при наличии страницы официального источника.

============================================================
6. РАЗВЁРНУТЫЕ ЗАДАНИЯ
============================================================

Критерии нельзя сокращать общими формулировками вроде:

- «есть существенное продвижение»;
- «выполнена часть решения»;
- «модель в целом верна»;
- «ошибка во включении границы».

Для каждого балла должна быть сохранена точная смысловая ветвь официальной таблицы.

Обязательно проверяются:

- все самостоятельные основания частичного балла;
- все альтернативные пути получения одного балла;
- граничные значения;
- обязательные рисунки;
- обязательные формулы;
- зависимости критериев;
- общие основания нуля.

Самооценка пользователя:

- всегда неофициальная;
- не заменяет эксперта;
- не должна формировать официальный результат;
- показывается отдельно;
- не скрывает общие основания нуля.

============================================================
7. ТЕХНИЧЕСКИЕ ЭВРИСТИКИ
============================================================

Технический счётчик не может считаться официальным алгоритмом.

К неавтоматизируемым условиям относятся:

- официальный подсчёт слов;
- определение авторских слов;
- проверка опоры на исходный текст;
- определение полного пересказа;
- оценка комментария;
- оценка доказательства;
- содержательная проверка рисунка.

Для таких условий:

- показатель маркируется как ориентировочный;
- правило ФИПИ показывается отдельно;
- вводится явное подтверждение пользователя;
- официальный балл не имитируется;
- тестируются все основания общего нуля.

============================================================
8. ЗАВИСИМЫЕ КРИТЕРИИ
============================================================

Каждая зависимость реализуется дважды:

1. в интерфейсе;
2. в функции расчёта.

Нельзя полагаться только на disabled-поле.

Scorer обязан независимо исключать недопустимое значение даже после ручной подмены сохранённого состояния.

Обязательны тесты переходов, перезагрузки и итоговой суммы.

============================================================
9. ИЗОБРАЖЕНИЯ
============================================================

SVG — часть содержания, а не украшение.

Обязательно:

- один канонический файл;
- автоматическое встраивание в T123;
- отсутствие ручного редактирования двух копий;
- проверка координат;
- проверка симметрии;
- проверка стрелок;
- проверка подписей;
- проверка осей и границ;
- проверка соответствия условию и решению;
- независимая визуальная сверка с PDF.

============================================================
10. СОСТОЯНИЕ ПОПЫТКИ
============================================================

Сохраняются:

- текущий номер;
- ответы;
- отметки;
- варианты «ИЛИ»;
- абсолютное время окончания;
- статус завершения;
- самооценка;
- зависимости критериев.

Обязательно:

- новый storage key для новой версии;
- try/catch для localStorage;
- запрет хранилища не ломает интерфейс;
- вариант «ИЛИ» не меняется после перезагрузки;
- тесты используют относительные пути;
- абсолютные пути /mnt/data/... запрещены.

============================================================
11. НАВИГАЦИЯ ЭКСАМИО
============================================================

- зелёный — ответ сохранён;
- оранжевый — отмечено для возврата;
- белый — ответа нет;
- синяя рамка — открытое задание.

Обязательны:

- номер задания;
- таймер;
- Предыдущее;
- Следующее;
- Отметить;
- Сбросить;
- Завершить или Проверить.

На ширинах 320, 360 и 390 px не должно быть горизонтального скролла.

============================================================
12. PREVIEW, MANIFEST И ZIP
============================================================

Preview автоматически создаётся из HEAD и T123 в порядке EXAM MAP.

Проверяется:

- каждый T123 присутствует ровно один раз;
- порядок совпадает;
- JSON разбирается;
- JavaScript проходит syntax check;
- нет незакрытых script/style;
- нет служебного текста;
- canonical один;
- нет года в постоянных SEO-полях;
- нет ошибок консоли.

Manifest создаётся последним.

ZIP собирается только по белому списку.

В ZIP запрещены:

- старые версии;
- PDF «ПРОЕКТ»;
- __pycache__;
- node_modules;
- временные логи;
- служебные архивы;
- абсолютные локальные пути.

После сборки ZIP распаковывается в чистую папку, и все тесты запускаются повторно.

============================================================
14. УРОКИ ИСПРАВЛЕННЫХ ПРЕДМЕТОВ
============================================================

Базовая математика:

Проблема — лишние accepted answers и размножение ложного объяснения по документации.

Защита — source locator для каждого ответа и обязательные негативные тесты.

Профильная математика:

Проблема — сокращённые критерии, неверные ветви частичного балла, самооценка в официальном итоге, проектный PDF.

Защита — критерии по баллам и ветвям, тест каждой ветви, expert_only, запрет проектных PDF.

Русский язык:

Проблема — технический счётчик стал официальным порогом, лишние символы очищались, общие нули реализованы не полностью.

Защита — advisory-only, строгая форма ввода, отдельные тесты каждого общего нуля.

Физика:

Проблема — правильный текст, но неправильные эталонные рисунки; отдельные и встроенные SVG расходились.

Защита — ASSET MAP, предметные инварианты, один канонический SVG, визуальная сверка.

Обществознание:

Проблема — зависимый критерий можно было обойти, полное условие показывалось после ответа, permissive-нормализация.

Защита — UI + scorer, полный prompt до ответа, тест переходов зависимых значений, строгая проверка.

============================================================
15. МОДУЛИ ДЛЯ НОВЫХ ПРЕДМЕТОВ
============================================================

Подключаются только при подтверждении формата документами ФИПИ.

Аудио:

- локальный файл;
- SHA-256;
- количество прослушиваний;
- сохранение состояния;
- отсутствие автозапуска;
- тест Chrome/Safari/mobile;
- рекламный звук не мешает.

Устная часть:

- микрофон только по действию;
- официальный тайминг;
- fallback при отказе;
- сохранение записи;
- отсутствие ложной автоматической экспертной оценки.

Файлы к заданиям:

- локальная копия;
- SHA-256;
- кодировка;
- целостность архива;
- правильная версия;
- negative test отсутствующего файла.

Информатика и программирование:

- официальная среда;
- изолированный запуск;
- запрет доступа к DOM, cookies, localStorage и сети;
- граничные тесты;
- отсутствие эталона в клиентском коде;
- честные ограничения без безопасной среды выполнения.

Карты, графики, таблицы:

- страницы источников;
- координаты;
- оси;
- подписи;
- единицы;
- границы;
- мобильная читаемость;
- отсутствие скрытого ответа в alt/title/имени файла.

Формулы:

- корни;
- степени;
- индексы;
- модули;
- ±, ≤, ≥, ≠;
- интервалы;
- экранирование JSON;
- тесты граничных значений.

============================================================
16. ПОРЯДОК РАБОТЫ НАД СЛЕДУЮЩИМ ПРЕДМЕТОМ
============================================================

1. Создать распакованный репозиторий предмета.
2. Скопировать стандартные шаблоны и скрипты.
3. Положить три финальных PDF в source/.
4. Рассчитать SHA-256.
5. Закрыть SOURCE GATE.
6. Заполнить EXAM MAP.
7. Заполнить TASK MAP.
8. Заполнить ASSET MAP.
9. Создать ACCEPTANCE CASES.
10. Провести независимую содержательную проверку.
11. Поставить CONTENT_LOCKED.
12. Создать предметный генератор T123.
13. Запустить unit-тесты.
14. Запустить browser smoke-test.
15. Автоматически собрать preview.
16. Автоматически создать manifest.
17. Автоматически собрать ZIP.
18. Запустить validator.
19. Распаковать ZIP в чистую папку.
20. Повторить тесты из ZIP.
21. Передать в Tilda со статусом READY_FOR_TILDA_TEST.
22. После публикации провести production smoke-test.
23. Только после этого поставить PUBLISHED_SMOKE_PASS.
